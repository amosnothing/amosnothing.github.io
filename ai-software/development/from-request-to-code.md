# 你说一句需求，AI 怎样改好代码：看懂 Codex 客户端与模型服务端的协作

**核心摘要**：你在 Codex 里输入一句需求，背后通常是一段反复往返的工作：客户端组织材料，模型根据材料判断下一步，工具读取和修改项目，再把真实结果交回模型。模型逐渐补齐对需求和代码的认识，直到交付改动，或遇到需要你决定的问题。

读完本文，你可以分清“谁在理解需求、谁在访问文件、谁在运行测试”，也更容易判断一次 AI 编程任务是否真的完成。本文以 Codex CLI 的公开机制说明基本过程；桌面端、编辑器扩展和云端任务的部署方式可能不同。

## 1. 概念解析与生活类比

### 先分清屏幕背后的三个角色

可以把一次 AI 编程任务，想成你向一位远程工程师交代工作：工程师需要项目材料，也需要有人或程序把他的操作落实到开发环境中。

| 角色 | 通俗理解 | 实际负责的事情 |
| --- | --- | --- |
| 客户端及其智能体运行程序 | 工作台和调度员 | 接收需求、组织上下文、请求模型、调度工具、展示进度与结果 |
| 模型服务端 | 提供模型推理的服务 | 接收请求、准备模型输入、运行模型，并返回文字或工具调用 |
| 项目与工具执行环境 | 能动手的开发现场 | 搜索和读取文件、应用修改、编译、运行测试，产生真实结果 |

这里把“客户端及其智能体运行程序”合称客户端，便于理解。它不只是一个聊天窗口。OpenAI 对 Codex 的工程说明，把用户、模型和工具之间的这段调度称为 **agent loop（智能体循环）**。[[1]](https://openai.com/index/unrolling-the-codex-agent-loop/)

在本文采用的本地执行、远程模型服务场景中，代码和测试进程位于你的开发环境，模型推理发生在服务端。云端任务可以把执行环境也放到远程；另外也有本地模型配置。因此，“客户端”“模型服务”和“执行环境”是三种职责，不一定对应三台电脑。[[1]](https://openai.com/index/unrolling-the-codex-agent-loop/)

### 它怎样“理解”你的一句话

假设你说：

> 用户搜索商品时，输入前后的空格不应该影响结果。请修复，保留原来的大小写匹配规则，并补上测试。

这句话至少包含四件事：修改搜索行为、处理首尾空格、保持大小写规则、增加验证。模型会结合这些要求、已有代码和后续反馈，形成对任务的判断。这里的“理解”可以从行为上检验：它是否找对入口、保留约束、处理正确输入，并给出可核对的结果。

在计算层面，大语言模型把输入转换为 token，再根据上下文生成后续内容。token 是处理文本的单位，并不等于一个完整的词。训练让模型学到语言和代码之间的关系，指令训练进一步帮助它按任务要求组织回答。对于这次搜索修复，需求中的每项限制都需要结合项目材料来落实。[[1]](https://openai.com/index/unrolling-the-codex-agent-loop/) [[2]](https://cdn.openai.com/papers/Training_language_models_to_follow_instructions_with_human_feedback.pdf)

模型不会直接知道你没说出的业务约定。例如，“只输入空格时应该返回全部商品还是没有结果”，上面的需求尚未说明。合理做法是先查现有约定；资料仍不足时，再向你确认。流畅地复述需求，不足以证明已经理解全部细节。

## 2. 核心价值与应用场景

### 第一步：客户端把需求与项目背景放到一起

同一句“修复搜索”，放到不同项目里，需要改的文件和验证方式完全不同。客户端会组织可用的任务材料；随着工作推进，模型也可以请求工具继续查找。

其中一类材料是项目说明。Codex 支持读取 `AGENTS.md`，把项目约定带入任务，例如使用什么测试命令、哪些接口需要兼容、哪些文件不能修改。这类说明影响模型的工作方式，但不能替代操作系统和工具层面的权限控制。[[3]](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

另一类材料是这次任务的现场信息：搜索入口在哪里、调用方传什么参数、已有测试如何规定大小写行为。它们通常要通过搜索、读取或用户提供，才会成为模型可使用的证据。**在客户端打开项目，不等于模型已经逐字读过整个仓库。**

### 第二步：请求里除了需求，还有“工具菜单”

可以把一次模型请求理解为一个材料包，而不是单独发送用户刚输入的那一句话。

| 材料 | 在商品搜索任务中起什么作用 |
| --- | --- |
| 任务与约束 | 处理首尾空格，保留大小写规则，补测试 |
| 项目说明与执行背景 | 告知工作目录、开发约定和可用环境 |
| 已选入的代码与对话 | 提供搜索实现、现有测试和你补充的要求 |
| 工具定义 | 告诉模型可以搜索、读取、编辑或运行什么，以及参数怎样填写 |
| 前面工具的结果 | 提供真实文件内容、修改状态、测试输出或错误 |

工具定义类似一份操作菜单：不只有“可以读取文件”，还会规定需要提供路径等参数。模型可以据此返回结构化的调用请求。OpenAI 的函数调用文档明确区分了模型请求调用工具，以及应用程序执行工具、回传结果这两个环节。[[4]](https://developers.openai.com/api/docs/guides/function-calling)

### 第三步：通过接口，反复交换材料和结果

API 可以理解成两端按约定收发消息的接口。下面把搜索修复任务拆成几次往返，展示谁发给谁、每次多知道了什么。工具名称、文件位置和顺序均为教学示例，不是实际抓包记录。

| 方向 | 传递的信息 | 随后发生什么 |
| --- | --- | --- |
| 客户端 → 模型服务端 | 需求、项目说明、工具菜单 | 模型判断先查搜索入口 |
| 模型服务端 → 客户端 | “搜索商品搜索相关代码”的工具调用 | 客户端调度搜索工具 |
| 客户端 → 模型服务端 | 搜索结果与相关文件内容 | 模型发现参数未经首尾空格处理，并继续核对调用方与测试 |
| 模型服务端 → 客户端 | 读取更多文件、添加测试和修改实现的调用 | 工具在项目中执行操作，返回成功或错误 |
| 客户端 → 模型服务端 | 修改结果和实际测试输出 | 模型根据失败信息继续修正，或检查最终差异 |
| 模型服务端 → 客户端 | 完成说明或需要用户决定的问题 | 客户端展示结果，用户可以验收或继续反馈 |

工具调用会带有标识，回传结果与对应调用关联，避免把另一项操作的输出接错。一次任务可以包含多次调用；每轮也不必只做一个动作。具体执行顺序和可并行范围由模型、运行程序与工具约定共同决定。[[4]](https://developers.openai.com/api/docs/guides/function-calling)

### 第四步：生成代码和维护代码，关键差别在哪里

生成新代码，需要从要求得到一份候选实现；维护旧代码，还要弄清“哪些行为不能改变”。对于搜索修复，不能因为要处理空格，就顺手把关键词全部转成小写，否则可能改变现有匹配规则。

因此，这次任务的合理验收可以包括：有首尾空格的关键词与去掉这些空格后的结果一致；没有首尾空格的输入保持原行为；大小写相关测试仍符合旧约定；纯空格输入遵循已确认的规则。这些验收条件来自需求和项目约定，不应由新实现自行定义。

模型可以提出修改，编辑工具把修改写进文件，测试进程再检查实际行为。如果测试命令未安装、执行失败或结果不符合预期，工具应把这些情况反馈回来。模型随后基于新证据继续工作。这个反馈过程，让编程工具能够超出“给你一段代码”的范围。

## 3. 最新演进与代表性实践

### 一次请求怎样变成界面里的进度

前面的搜索修复任务，会被拆成多次结构化请求。在 Codex CLI 公开的实现中，客户端通过 Responses API 发送指令、材料和工具定义；服务端组织模型输入，再把生成的文字或工具调用分段返回。工具执行结果随后进入新的请求，让模型继续工作。[[1]](https://openai.com/index/unrolling-the-codex-agent-loop/)

界面上逐步出现的文字，是服务结果可以分段传回、由客户端陆续展示的一种表现。用户看到的进度文字和操作记录，也不能当成模型内部全部计算的逐字转录。

### 为什么长任务要整理上下文

代码、日志和对话不断增加，单次模型处理的信息有长度限制。上下文压缩可以用更少的 token 携带后续工作需要的状态，但不能保证所有历史细节都被无损保留。[[5]](https://developers.openai.com/api/docs/guides/compaction)

可以把它想成工程师交接班时整理工作记录：目标、已完成修改、失败原因和待办事项应留下。关键约定最好同时保存在项目资料和测试中，需要时再读取核对。

### 缓存让重复材料少算一些

连续请求常会共享一段相同的开头。提示缓存可以复用这段前缀的计算结果，减少重复处理。它提高的是计算效率，不能说明模型永久记住了你的项目，也不等于已经验证后续代码正确。[[6]](https://developers.openai.com/api/docs/guides/prompt-caching)

如果想进一步比较 Claude Code、Codex 与 DeepSeek Harness 的设计，可以接着阅读 [Harness 工作原理](/ai-software/agent-harness/)。

## 4. 常见认知误区与使用边界

### 服务端返回了改法，不代表本地已经修改

“模型建议去掉关键词首尾空格”“模型发出了编辑调用”“文件修改成功”“测试验证成功”，是四种不同状态。验收时需要查看实际差异与执行结果，不能只依据最后一句“已完成”。

### 模型想做什么，与工具允许做什么，是两回事

模型可能请求访问某个目录或运行一条命令，执行环境仍需决定是否允许。Codex 官方说明把沙箱与审批分开：沙箱限制命令能访问哪些文件和网络资源，审批决定何时需要对操作进行批准。具体限制取决于当前配置和使用入口。[[7]](https://learn.chatgpt.com/docs/sandboxing)

因此，项目说明里写“不要修改其他项目”，与执行环境真正限制跨项目写入，是不同层面的措施。外部工具也需要遵循自己的权限与授权约定。

### 使用本地客户端，不代表所有信息都留在本地

在远程模型服务场景中，进入模型请求的需求、代码片段和工具输出，需要传给相应服务。另一方面，这不等于每个本地文件都会上传。具体发送范围取决于材料选择和工具流程；数据保留、训练使用和组织管理策略，还要分别查看所用服务及账户的正式说明，不能从“本地执行”推断出来。

### 怎样让它更容易做对

与其只说“搜索不好用，帮我优化”，不如交代：哪个输入触发问题、现在得到什么、期望得到什么、哪些行为必须保持，以及怎样判断修复成功。业务规则缺失时，允许它查资料或向你确认。

收到结果后，按四件事核对：需求是否被正确转成行为，修改是否落在正确位置，实际执行了哪些验证，还有哪些情况未验证。这比只看代码长度或回答是否自信，更能判断这次协作的质量。
