# CC、Codex、DeepSeek Harness 是怎么和模型配合干活的

**核心摘要**：你让编程工具修一个 bug，背后通常会发生多次模型请求。模型根据手里的材料提出下一步，工具在具体环境里执行，再把结果交回去。理解这段往返，比记住几个产品名字更有用。

## 1. 概念解析与生活类比

### 先把三个名字分清

CC 是 Claude Code 的常见简称。本文说的 Codex 是 OpenAI 的编程工具，主要借助 Codex CLI 的公开说明解释原理。DeepSeek Harness 则是 DeepSeek 开发的智能体框架，命令名是 `dsh`。三者都包含模型之外的程序，负责组织工作过程。[[1]](https://code.claude.com/docs/en/how-claude-code-works) [[2]](https://openai.com/index/unrolling-the-codex-agent-loop/) [[3]](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.zh.md)

| 名称 | 它是什么 | 阅读资料时别混淆什么 |
| --- | --- | --- |
| Claude Code | 使用 Claude 模型完成任务的工具 | Claude 是模型系列，Claude Code 是围绕模型运行的软件 |
| Codex | 有 CLI、编辑器等使用入口的编程工具 | 产品名与一次请求实际选用的模型，需要分别看 |
| DeepSeek Harness | 以插件组织能力的开源框架 | DeepSeek 模型和 DeepSeek Harness 是两回事 |

Harness 这个词可以先理解成“让模型干活的那套程序”。它准备材料、发送请求、接收工具调用、安排执行、保存记录，再决定是否继续。

拿一次故障排查来类比：有人负责看日志、判断原因、提出操作；还需要终端、代码仓库、测试环境和执行记录。模型承担分析和生成建议的部分，harness 把建议接到这些实际设施上。这个类比只用来理解分工，具体步骤也可能由程序预先安排。

### 模型能看到多少，取决于送进去了多少

在电脑上打开一个仓库，不等于模型已经读过全部源码。文件要经过读取、搜索或其他处理，相关内容才会成为模型这次请求的输入。工具有权访问某个目录，也不等于目录里的内容已经出现在上下文中。

可以把上下文当成这次排查的材料包。包里漏掉了接口约定，模型就可能按常见写法猜；包里混着旧需求和新需求，它就可能沿着错误版本修改。因此，先确认它读到了什么，往往比再说一遍“仔细想想”管用。

## 2. 核心价值与应用场景

### 跟着一个 bug 看完整过程

假设用户提出：

> 订单列表为空时，导出会报错。请修好，保留原有列名和顺序。空列表也要导出带表头的文件。

下面是一个教学示例。工具名和步骤顺序经过简化，不对应某个产品的逐字运行记录。

| 轮次 | 交给模型的材料 | 模型提出的下一步 | Harness 和工具实际做的事 |
| --- | --- | --- | --- |
| 1 | 用户要求、项目说明、可用工具说明 | 搜索导出入口 | 搜索文件，返回路径和匹配内容 |
| 2 | 上一步的搜索结果 | 读取实现和相关测试 | 读取文件，返回代码 |
| 3 | 代码、已有测试、接口约定 | 补上空列表用例，先运行 | 写入测试，启动测试进程，返回失败信息 |
| 4 | 失败位置和报错 | 修改生成表头的逻辑 | 应用修改，返回操作结果 |
| 5 | 修改结果 | 重跑空列表和正常列表用例 | 返回实际测试结果 |
| 6 | 测试结果、最终改动 | 向用户说明原因和验证情况 | 展示改动和完成说明 |

这段“请求模型 → 执行工具 → 回传结果 → 再请求模型”的往返，叫作 **agent loop（智能体循环）**。Codex 的公开工程说明直接描述了这个过程；Claude Code 的文档则把任务概括为收集信息、采取行动和验证结果。[[2]](https://openai.com/index/unrolling-the-codex-agent-loop/) [[1]](https://code.claude.com/docs/en/how-claude-code-works)

你看到它工作了几分钟，可能是在等待测试、读取输出、重新组织请求。耗时需要结合执行记录判断。

### 一次请求里装了什么

各家接口字段不同，可以先按下面几类理解：

- **任务和约束**：要解决什么，哪些行为必须保留。
- **当前材料**：已经选入的代码、日志、对话和工具结果。
- **工具说明**：有哪些工具、分别做什么、参数怎么填写。
- **执行背景**：当前目录、运行环境，以及适用于当前任务的规则。

工具说明中可能有“读取文件”这一项，并要求提供路径。模型返回的工具调用，就相当于一张结构化的操作单：工具名是什么，参数是什么，本次调用的编号是什么。程序收到后，校验并执行，再把结果和对应编号送回去。DeepSeek 的 Tool Calls 示例明确说明，具体函数由调用方提供，模型本身不执行该函数。[[4]](https://api-docs.deepseek.com/guides/tool_calls/)

这里要分清三个状态：“建议运行测试”“发出了测试调用”“测试确实结束并通过”。只有最后一个状态包含了执行结果。模型说“准备修改文件”，同样不能证明文件已经改过。

### 为什么还需要权限和停止条件

模型可以提出删除目录的操作，执行程序仍需依据权限决定是否放行。参数是否合法、路径是否允许、命令是否超时，都需要在执行环节处理。本文建议把这些要求落到程序和环境设置中，不能只在提示词里写一句“不要误删”。

循环也要有结束的办法：模型给出答复、用户取消、工具失败，或者达到预算和轮数限制，都可能让任务停下来。具体实现因工具而异。停下来只说明这一轮执行结束，业务问题是否解决，还得看验收结果。

## 3. 最新演进与代表性实践

以下产品说明核对于 2026 年 11 月 26 日，重点看各自公开的设计，不作能力排名。

### Claude Code：把项目工具接到 Claude 上

Claude Code 官方文档将其定位为围绕模型的一层程序，管理工具与上下文。文件操作、搜索和命令执行构成了日常开发的基础，扩展能力可以通过 skills、MCP 和 hooks 等方式接入。[[1]](https://code.claude.com/docs/en/how-claude-code-works)

用它排查问题时，可以顺着记录看：读了哪些文件，执行了什么，结果如何。结论有疑点，就回到对应步骤核对。

### Codex：公开拆解请求和结果的往返

OpenAI 在 2026 年 1 月发布的工程文章中，展示了 Codex 如何组织发给 Responses API 的请求，以及如何把工具结果带入下一次请求；文章还介绍了缓存与上下文压缩。这里解释的是公开设计，具体客户端与版本的细节可能继续变化。[[2]](https://openai.com/index/unrolling-the-codex-agent-loop/)

这也解释了一个常见现象：聊天界面里仍能翻到早期内容，模型当前使用的材料却可能已经经过压缩。历史记录、当前上下文和仓库文件，是三份需要分别理解的信息。

### DeepSeek Harness：框架和模型可以分开配置

DeepSeek Harness 的官方仓库采用“一切皆插件”的设计。截至核对时，README 仍标为开发者预览，并提示后续可能出现破坏兼容性的变更。[[3]](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.zh.md)

它还区分官方模型和自定义模型服务。官方说明写明，自定义模型由用户配置相应 API，输入会发送给所配置的模型。这意味着使用 DeepSeek Harness 时，应单独确认当前选中的模型服务。[[5]](https://www.deepseek.com/harness/privacy/)

若自己开发接入程序，还要核对模型接口的具体约定。例如 DeepSeek 当前的 Chat Completion 思考模式，在请求携带 `tools` 时，要求按文档保留并回传历史 `reasoning_content`。只替换服务地址，未必完成了适配；这条要求也不能套到所有厂商和所有接口上。[[6]](https://api-docs.deepseek.com/guides/thinking_mode/)

## 4. 常见认知误区与使用边界

### 同一个模型，换个工具为什么表现不同

可以从前面的执行过程推出来：即使模型相同，两套工具提供的材料、工具说明、错误反馈、执行环境和结束条件也可能不同。某个工具能快速定位调用方，另一个只给出文件名，模型下一步的依据就已经不同。

团队比较工具时，建议固定仓库版本、任务和验收条件，再记录完成率、实际耗时、费用与人工返工量。只比较一段回答写得顺不顺，看不出它是否保留了接口兼容性。

### 规范文件、Skill、MCP、Hook 各管什么

这几个词常一起出现，可以按用途区分。具体加载方式和优先级，以所用工具的文档为准；下面是工作分工的简化说明。

| 名称 | 用在什么地方 | 放到导出故障中看 |
| --- | --- | --- |
| 项目规范文件，如 AGENTS.md、CLAUDE.md | 交代项目约定和工作要求 | 说明列名属于公开接口，修改前要核对 |
| Skill | 复用某类任务的步骤和资料 | 给出报表故障的排查方法 |
| MCP | 连接外部工具或资料服务 | 让工具能查询缺陷记录或接口文档 |
| Hook | 在指定事件发生时触发预设动作 | 编辑完成后触发格式检查，具体取决于配置 |

写进规范的测试命令，要有人或程序真正执行，才会产生检查结果。接入一个缺陷系统，也要查询到这次问题的记录，模型才有相应依据。它们各自解决一部分工作，接好之后仍需查看执行情况。

### “测试全绿”还要多问一步

继续看空列表导出的例子。如果实现和测试都把“没有订单就不生成文件”当成正确行为，测试可能全部通过，用户的要求却没实现。

验收时应回到原始约定：空列表是否仍有表头，列名和顺序是否保留，正常列表是否受影响。测试里的预期结果要有依据，否则只是在验证实现和自己的假设一致。

### 软件从业者可以直接用上的做法

下面是结合上述机制给出的工作建议。

- **产品和业务人员**：提供能判对错的例子。把“导出正常”写成“零条数据仍有表头，列顺序与正常文件一致”。
- **研发人员**：同时核对调用方和被修改的实现。模型找到故障点后，还要看谁依赖原有行为。
- **测试人员**：保留修复前会失败、修复后会通过的用例，再检查预期是否来自需求。
- **技术负责人**：用同一批真实任务比较工具，记录返工和审查成本，把这些计入效率。

交付说明也可以固定问清四件事：改了什么，为什么这样改，实际验证了什么，还有什么没验证。这样更容易决定下一步是合并、补测，还是退回修改。
