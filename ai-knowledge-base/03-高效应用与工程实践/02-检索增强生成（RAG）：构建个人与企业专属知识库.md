# 检索增强生成（RAG）：构建个人与企业专属知识库

> **核心摘要**：RAG 在生成答案之前，先找出与问题有关的外部资料。效果要分别检查资料、检索与生成，不能只看答案末尾有没有链接。
>
> 核验日期：2026-11-27。检索流程是常见设计，具体指标须按业务标注与评测条件解释。

## 从一个报销问题看资料如何进入回答

员工问“上海出差能报多少住宿费”，系统需要找到当前有效、适用员工和地区的制度，再把条款交给模型解释。2020 年的 RAG 论文研究了参数化模型与外部检索的组合；今天常说的 RAG 系统范围更宽，不一定复现原论文的训练结构。[[1]](https://arxiv.org/abs/2005.11401)

## 入库时为什么要切分

制度通常要拆成便于检索的 **chunk（片段）**。拆得太短，“每日 500 元”可能丢掉地区和适用人群；拆得太长，一次返回大量无关条款。应尽量沿标题、条款和表格边界组织，保留文档版本、条款位置、生效时间和权限。这是设计建议，合适长度需要实测。

重叠片段可减少跨边界遗漏，也会增加重复内容。表格尤其要保留表头与单位，不能把金额和对应地区分开索引。

## 召回与重排分别解决什么

常见流程可以看成两轮筛选：

| 步骤 | 工作 | 报销例子 |
| --- | --- | --- |
| 过滤 | 限定用户权限与有效资料 | 排除无权查看的文件和失效版本 |
| 召回 | 从大库中找候选 | 关键词查“上海”；向量检索查意思相近的“住宿上限” |
| 重排（rerank） | 更细地比较问题与候选片段的相关性 | 把真正适用的住宿条款排到前面 |
| 生成与引用 | 用选中资料回答并标出依据 | 说明适用范围、金额与条款位置 |

**混合检索**可结合关键词与向量方法。前者适合精确名称、编号，后者帮助找到表达不同但意思相关的内容；重排只在候选里选，无法凭空补回完全漏掉的证据。

Anthropic 的 Contextual Retrieval 工程实验在片段中加入解释性上下文，并比较检索与重排组合。它提供实现思路，厂商报告的改善幅度不应直接当作所有知识库的预期收益。[[2]](https://www.anthropic.com/research/contextual-retrieval)

## 验收要拆成几张成绩单

以下指标约定用于解释评测，不是固定行业门槛：

| 检查对象 | 指标或方法 | 能说明什么，不能说明什么 |
| --- | --- | --- |
| 召回 | Recall@k：前 k 个候选找回的相关证据数／标注相关证据总数 | 衡量找回完整性；必须先约定相关证据及去重方法 |
| 排序 | 查看正确条款是否在前几位，可用 MRR 或 nDCG | 衡量位置；相关性好不等于条款对当前用户有效 |
| 忠实性 | 答案中的关键主张能否由选中材料支持 | 检查是否擅自补充；材料本身错误时仍可能忠实但不真实 |
| 正确性与拒答 | 人工参考答案、无答案问题和版本冲突样本 | 检查业务要求和缺资料时的表现 |
| 成本 | 全流程延迟、费用与人工返工 | 不能只统计最后生成回答的时间 |

假设标注了 4 份相关证据，前 5 个候选找到其中 3 份，Recall@5 就是 3/4。若只要求命中任一正确片段，那是另一种命中率口径，不应也叫同一个 Recall@k。没有标全的证据集会限制指标可信度。

Ragas 研究将检索上下文、答案忠实性与生成质量分开评估。自动评分适合辅助定位问题，不能仅因评分器也是模型，就免去人工抽查；它也可能受材料与任务变化影响。[[3]](https://arxiv.org/abs/2309.15217)

## 找到了资料，仍可能在哪里失败

**资料错误、检索遗漏、适用范围判断错误、答案过度推断**都可能出现在同一条链路。建议保留旧版混淆、跨地区、无权限和无答案问题作为测试样本。权限应在检索与输出环节实际执行，不能只要求模型“不要泄露”。

资料较少且联系紧密时，整份放入上下文也是选项。要根据规模、更新频率和权限复杂度比较方案，不能仅凭窗口更长就决定弃用检索。
