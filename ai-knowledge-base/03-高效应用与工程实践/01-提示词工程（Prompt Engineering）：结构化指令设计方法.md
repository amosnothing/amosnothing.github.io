# 提示词工程（Prompt Engineering）：结构化指令设计方法

> **核心摘要**：提示词的作用是交代目标、材料、约束和验收方式。写得清楚可以减少歧义，效果是否改善仍要用任务检验。
>
> 核验日期：2026-11-27。厂商指南作为方法参考，本文模板未做跨模型效果实验。

## 先写清什么算做对

“整理一份纪要”有很多合理理解。面向未参会成员、只用附件、区分建议与决定，再规定负责人缺失时写待确认，验收就具体得多。Anthropic 的提示词指南也将成功标准和可执行评估列为优化前提，但这属于实践指南，不是万能模板的实验结论。[[1]](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview)

可以按任务需要交代以下内容，简单问题不必填满整张表：

| 要素 | 要说明什么 | 纪要任务中的例子 |
| --- | --- | --- |
| 目标与读者 | 帮谁完成什么 | 让未参会成员知道下一步 |
| 证据范围 | 允许依据哪些材料 | 只用所附录音转写与决议附件 |
| 任务与边界 | 要做什么、不能补什么 | 提取行动项，不新增承诺 |
| 输出 | 怎样呈现 | 决定、行动项、待确认问题 |
| 验收 | 怎样判对错 | 责任人和期限与原文一致 |

## 示例为什么有用，又会带来什么偏差

给出一两个“输入—期望输出”的示例，可以展示分类和格式，这叫 **few-shot prompting（少样本提示）**。GPT-3 研究检验过上下文示例对特定任务的影响；实际效果随任务、示例和模型而变。示例是在本次输入中提供线索，不等于重新训练模型。[[2]](https://arxiv.org/abs/2005.14165)

如果每个示例都把“建议”归为“决定”，模型可能照着错误模式做。示例应包含容易混淆的情况和无答案情况，而不只是几个最简单的成功案例。

## 一个可以直接改用的任务说明

> 请依据所附会议记录，面向未参会的项目成员整理纪要。分别列出已确认决定、行动项和待确认问题。每项行动写明负责人和期限；原文未说明时写“待确认”。重要结论附原文位置，不把建议改成决定，不补充附件以外的承诺。

这是协作示例，不是效果保证。若输入本身缺页、转写错误或无法分清说话人，应先处理资料问题；再强调“务必准确”不能补齐缺失事实。

## 怎样判断改过的提示词更好

本文建议保留一组真实样本，涵盖常见、例外和无答案任务：

1. 固定模型版本、资料、工具与评分表。
2. 比较改前与改后的结果，一次优先调整一个重要因素。
3. 记录事实错误、要求遗漏、人工修改量、总耗时与费用。
4. 模型或资料变化后复测，不把一次满意回答当作长期结论。

安全要求应在应用里落实。提示词可说明“只查询本人权限内的资料”，但真正过滤权限、限制写操作仍是系统职责；外部文档中的要求也不能自动升级成用户授权。OWASP 的注入指南描述了这类信任边界问题。[[3]](https://genai.owasp.org/llm2026/llm012026-prompt-injection/)
